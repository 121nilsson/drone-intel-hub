## Architecture

- Feature-Sliced: features live in src/features/<slice>, shared contracts in src/shared/contracts, entities in src/entities — keeps slices decoupled.
- Layers stack downwards and nothing reaches back up: src/entities (pure domain) → src/shared/contracts (interfaces) → src/shared/infra (implementations and shared application services) → src/shared/ui (shared widgets) → src/features/<slice> (slice UI) → src/routes. A feature may not import another feature, and src/shared and src/entities may not import src/features — so code two slices need lives in shared/, not in one slice's pocket.
- Those boundaries are enforced, not merely described: eslint-rules/index.js adds no-cross-feature-import, no-lower-layer-feature-import, no-server-import-from-client and no-nordic-ui-copy to the lint run, so a violation fails the build instead of waiting for a reviewer to notice.
- Features depend only on contracts (DroneRepository, IntelExtractor, BriefingSummarizer, CatalogMutations); concrete implementations are chosen solely in src/shared/infra/services.tsx — so storage/inference can be swapped without touching features.
- A page asks for an operation, never for the parts it works on: the catalog page calls svc.catalog.merge(...) rather than assembling the repositories, and the dossier calls svc.catalog.removalImpact(id) — so the implementation stays behind the contract and the call site stays readable.
- External AI calls go through the chatCompletion server function proxy — keeps provider calls off the browser.
- Persistence goes through the async DocumentStore contract (src/shared/contracts/store.ts); repositories are write-through caches that attach a store at startup — so localStorage, PostgreSQL or any DB swap without touching features.
- A document write carries the revision the cache last read (`put(collection, doc, expectedRev)`); a conflict reloads and reapplies the caller's replay function, and a cache that cannot reapply keeps the stored copy rather than the unsaved edit — so two tabs cannot silently replace each other's whole-document writes. The revision lives in the store, never in `updatedAt`; PostgreSQL and browser storage enforce it, while the Lovable Cloud backend reports revision 0 and remains last-write-wins until its managed schema gains a revision column.
- Storage failures are visible, not silent: a rejected put/remove, a dropped conflict and a failed attach are reported to the shell. The composition root never falls back from server storage to localStorage on its own; an unreachable status call or a partial attach shows the storage error and offers browser storage as an explicit choice, so the analyst never unknowingly edits a second catalog.
- PostgreSQL is selected automatically when the server has DATABASE_URL; schema lives as plain portable SQL in /migrations (also mounted by docker-compose) — keeps the DB vendor-neutral and self-hostable.
- /migrations are applied at server start (plugins/migrate.ts → postgres/migrate.server.ts, recorded in schema_migrations, one transaction, requests wait on it); every file must stay idempotent because adopting an existing database re-runs them all once.
- Server-only DB code lives in *.server.ts files and is dynamically imported inside server-function handlers — keeps the driver out of the browser bundle. A browser-reachable module may not import a *.server module by value (a type-only import is erased at build and stays allowed).
- Ingestion is two-stage: collectors only store raw posts as pending dispatches (no AI); a bounded processor drains the queue and records provenance — keeps scraping fast and AI work resumable. The pipeline itself lives in src/shared/infra/ingest, because the queue, the catalog pages and the server-side collectors all drive it.
- Shared storage selection happens in store.functions.ts: DATABASE_URL → PostgresStore, else Lovable Cloud → CloudStore (server-only, service role; tables have RLS with no client policies) — browser never talks to the DB directly.
- Language vocabulary (money, units, cues) lives in per-language lexicons in src/shared/lexicons, shared by heuristic extractors and normalization; heuristics are split into names, facts orchestrator and per-class/fact-family extractors that read only lexicons — adding a language, term or system class never touches unrelated code.
- Page copy is English, and that is enforced too (no-nordic-ui-copy): a Russian or Ukrainian system name is data and may appear verbatim in the UI, but a Swedish word in a UI string is a mistake. Foreign words that are genuinely data (the Swedish lexicon, the stopword corpus in shared/lexicons/fillers.ts) live in the lexicon layer, where the rule does not reach.
- Financial/deal spec keys (contract_value, *_funding, total_cost…) are split out of extractions at the pipeline boundary (entities/procurement/routing.ts) into the procurements collection; only unit_cost stays a drone spec — keeps deal figures out of consensus.
- Activity figures (launched, intercepted, delivered, produced, kills, ordered — "launched more than 2,800 in August") are not properties of a system: `mergeSpecs` splits them out at every ingest path into `Drone.activity` (entities/drone/activity.ts), each with its quantity, bound, counted unit and period, and the catalogue repair moves ones stored as specs. Consensus never reads activity; it is a series, shown in the dossier's Activity panel. An attribute that only mentions an event (launch weight, production timeline) stays a spec.
- Relations between entries are typed and directed (`Drone.relations`, `SystemRelationClaim`; entities/drone/system-hierarchy.ts): `variant_of`, `derived_from`, `subsystem_of`, `effector_for`, `carried_by`, stored once on the entry that depends on the other, and `counterpart_to`, stored once for both. The other end reads them through the inverse (`has_variant`, `parent_of`, …), which is never stored. `systemClass` says what an entry is; a `family` (Geran, Shahed) is an umbrella its variants point at. system-hierarchy.ts is the one reader - the dossier, the counterparts page, catalogue cards, the related-intel graph and the briefing digest all go through `resolveRelations` - and it reads the legacy `variantOfId`/`variantIds`/`counterpartIds` with them until the repair has copied those over; catalogue operations (`linkSystems`, `unlinkSystems`, `reviewRelation`, merge, remove) write both and unlink both sides, so a legacy link left behind cannot be revived. Inherited specs exist only in a comparison view (`compileEffectiveSpecs`), never in an entry's own specs or in consensus.
- Family clean-up is proposed, never applied (`familyProposals`, entities/drone/family-audit.ts; the Families page): an entry two or more others are numbered after is a family, a numbered entry not linked to it is its variant, an alias that is another entry's name or a designation on a family is misfiled, and an entry sharing most of a family's names is a merge. Each proposal is an existing catalogue operation the analyst runs; a turned-down one is recorded (a rejected relation, `distinctFrom`, a reviewed alias) and not proposed again. Identity is the high-risk tier: nothing here runs unattended. The catalogue repair copies legacy links into typed relations (`legacyRelationsToMigrate`), once each, never a second family.
- Layout primitives (Card, CardGrid, ListRow, Panel, PageTitle in src/shared/ui/primitives.tsx; ExternalSourceLink, SystemChip in src/shared/ui/links.tsx) own mobile width rules — pages compose them instead of hand-rolling card/row layouts, so a fix lands once. Widgets several slices share (the related-intel graph, the translate button) live in src/shared/ui for the same reason.
- Heuristic evaluation (src/shared/infra/evaluation) is read-only: it only calls heuristic.extract and reads candidates; agreements export to src/test/fixtures/eval-corpus.json, which eval-corpus.test.ts replays — so heuristic changes can't silently regress real reports.
- Dynamic heuristic rules live in dynamic_rules (migration 010) and reach the engine only as an immutable RuleSnapshot (src/shared/contracts/rules.ts); the server registry (shared/infra/heuristics/rule-registry.server.ts) refreshes it by version with a TTL and never throws — so extract() stays synchronous/pure and ingestion survives DB outages.
- A dynamic rule becomes active only through the in-process sandbox (src/shared/infra/evaluation/sandbox.ts, read-only): zero fixture regressions, no F1 drop, a measurable gain — and activation re-runs it against the rules active at that moment (shared/infra/evaluation/rule-sandbox.server.ts). The DSL carries literal terms only, never regex — so generated rules cannot backtrack or reach outside the words they name.
- After an AI pass, each stored spec records the AI's verdict on the heuristic's observation in `provenance` (both/heuristic/ai; entities/drone/extraction-gates.ts), and evaluation scores AI-dropped claims as rejected — so the heuristic is never measured against its own ingest-time output while the stored union still never drops a deterministic fact.
- Generated rules go sandbox → shadow → active; auto-promotion (shared/infra/evaluation/autonomy.ts) needs 48 h shadow on unseen reports, zero conflicts, ≥95 % shadow precision and ≥95 % trust from ≥20 analyst decisions in the category, max 2/day, and a nightly circuit breaker compares all-active vs active-minus-last-24h on the same sample — so autonomy is earned per category and rolled back on harm, never on data drift. `RULES_AUTOPROMOTE=off` disables it.
- An analyst's verdict on a spec claim lives on the claim (`SpecClaim.review`, entities/drone/claim-review.ts), never in a separate table, and outranks every automated verdict; it is the ground truth the automation is scored on: evaluation references (`referenceSpecs`), live regression fixtures (`analystFixtures`) and the trust of the contradiction check — so one person's correction reaches every loop, works in every store and survives re-analysis.
- A claim the analyst says belongs to another attribute is moved, not just ruled out (`moveClaim`, entities/drone/claim-review.ts): it keeps its place in the report, stops counting on the attribute it was misfiled under, and is filed under the attribute the analyst names, with the reading the analyst gives — because a speed read as a height is not a wrong figure, and ruling it out alone would throw the figure away. Undoing the verdict undoes the move with it, and the filed copy is the analyst's own claim, so a re-read of the post leaves it alone. A unit fix never counts as agreement with such a verdict: it would have applied a value to a figure that does not belong there.
- Unit slips and impossible figures are found deterministically (entities/drone/auto-correction.ts) and recorded as `SpecClaim.autoCorrection`; the sync job (shared/infra/ingest/auto-correct.ts) applies a kind of correction only while analysts' answers on it meet the earned-trust bar (shared/infra/ingest/earned-trust.ts), recomputed every run — so a correction is a proposal until earned, rolled back when agreement falls, and `AUTOCORRECT=off` keeps every one a proposal.
- A payload or a sensor reaches the catalogue twice: as an observation (what a report said the system carries) and as a spec (the figure — payload capacity, warhead mass, camera count). The panels read both (entities/drone/observations.ts), because the observation lists are thinly filled and the specs are where most of that knowledge is; the prompt says which is which (shared/contracts/extraction-prompt.json), so a list of what the system carries never becomes a spec and a figure never becomes a list.
- Names match after a system's name only through real Russian/Ukrainian case endings, the bare stem and the English plural (`CASE_ENDINGS`, entities/drone/name-key.ts), never "any few letters": that read "контракт" (contract) and "contrast" as Contra and "лютого" (February) as Lyutyi. A change to name matching is an identity change: measure it over the archive before it ships.
- Every machine claim carries a deterministic verdict (`SpecClaim.verification`, entities/drone/verification.ts): quote in the post, unit, bounds, and identity — anchored to the sentence carrying the quote, matched with the extractor's own `mentionsName` (entities/drone/name-key.ts) over the same `catalogNames` (entities/drone/catalog-names.ts), and `uncertain`, never `pass`, when that sentence names no system. It shows the extractor read the post correctly, not that the post is right, and it is measured only: `claimCounts` does not read it, so an uncertain or rejected claim still counts in consensus until a later phase of get_human_out_of_the_loop_plan.md says otherwise. Bumping `VERIFIER_VERSION` re-verifies the catalogue. With PostgreSQL that run is on the server (`verification:run`, hourly; shared/infra/verification/verify.server.ts), reading post text straight from the archive, because the store caps the dispatches it loads and a run over the browser's window judged older claims "not in the archive"; in browser storage the backfill runs in the browser in yielding chunks; against a last-write-wins store it runs only when asked. Either way it and never re-judges without its post a claim that was checked against one (a pruned post, an unarchived paste). Claims carry the archived post they came from (`sourceId`, stamped through the intake queue by `Candidate.dispatchId`); older claims written without it are linked back by their unique `outlet · URL` source before they are verified.
- Autonomous decisions are written to `autonomy_events` (migration 018, shared/infra/autonomy/ledger.server.ts) with actor, target, before/after and a `reversed_by` link; decision events are kept forever and only the kinds in `HEARTBEAT_EVENT_KINDS` are pruned. An event kind is added to `AUTONOMY_EVENT_KINDS` in the same change as the code that writes it.
- How often `verified` is right is measured by a person, never assumed (`/audit`; entities/drone/audit.ts, shared/infra/verification/audit.server.ts, migration 019): the system draws verified claims at random with a recorded seed, the person answers one question per claim, hidden controls catch an inattentive batch, and an exact binomial stopping rule decides pass or fail against the low-risk budget. An audit answer measures the verifier and never becomes `SpecClaim.review`, and the frozen seed set lives only in `verification_audit` — every learning loop reads the analyst's review, and nothing that learns may read the seed set.
- A second reader checks what the deterministic checks leave uncertain (`SpecClaim.entailment`; entities/drone/entailment.ts, shared/infra/verification/entailment.server.ts, `verification:ai` hourly): a model that extracted none of the post's claims, shown the post and the bare claims but never the extractor's quote, answering with a passage that must be in the post or the answer is `uncertain`. Its spend is counted per day in `ai_token_usage` (migration 020) and stops at the ceiling (`VERIFIER_DAILY_INPUT_TOKENS`/`_OUTPUT_TOKENS`). It is measured, not acted on: no claim's state and no consensus reads it until its agreement with the person's audit answers (the Audit page) says its "supported" can be trusted; `AI_VERIFIER=off` stops it.
