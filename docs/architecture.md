# Architecture

The detail behind the rules in [AGENTS.md](../AGENTS.md). AGENTS.md keeps the rules that fail the
build or corrupt data; each area below keeps its reasons, its file names and its history. A path
named here is checked by `src/test/docs-paths.test.ts`, so it cannot quietly go stale.

## Layers and composition

How code is placed, and what is enforced rather than described. See also the `layer-boundaries` skill.

- Feature-Sliced: features live in src/features/<slice>, shared contracts in src/shared/contracts, entities in src/entities — keeps slices decoupled.
- Layers stack downwards and nothing reaches back up: src/entities (pure domain) → src/shared/contracts (interfaces) → src/shared/infra (implementations and shared application services) → src/shared/ui (shared widgets) → src/features/<slice> (slice UI) → src/routes. A feature may not import another feature, and src/shared and src/entities may not import src/features — so code two slices need lives in shared/, not in one slice's pocket.
- Those boundaries are enforced, not merely described: eslint-rules/index.js adds no-cross-feature-import, no-lower-layer-feature-import, no-server-import-from-client and no-nordic-ui-copy to the lint run, so a violation fails the build instead of waiting for a reviewer to notice.
- Features depend only on contracts (DroneRepository, IntelExtractor, BriefingSummarizer, CatalogMutations); concrete implementations are chosen solely in src/shared/infra/services.tsx — so storage/inference can be swapped without touching features.
- A page asks for an operation, never for the parts it works on: the catalog page calls svc.catalog.merge(...) rather than assembling the repositories, and the dossier calls svc.catalog.removalImpact(id) — so the implementation stays behind the contract and the call site stays readable.
- External AI calls go through the chatCompletion server function proxy — keeps provider calls off the browser.
- Layout primitives (Card, CardGrid, ListRow, Panel, PageTitle in src/shared/ui/primitives.tsx; ExternalSourceLink, SystemChip in src/shared/ui/links.tsx) own mobile width rules — pages compose them instead of hand-rolling card/row layouts, so a fix lands once. Text that comes from outside (a model brief, a post) goes in `Prose` (wraps anywhere, so one URL cannot widen the page), anything long is cut by `Collapsible` behind "Show more" (`ExpandableText` is one paragraph of it), a table is `DataTable` (phone cards come from its columns unless the page draws its own, `cards={false}` opts out), and the phone menu is `MobileDrawer` on the shared Sheet. `main` clips sideways overflow as a safety net; `npm run check:mobile` (scripts/check-mobile-width.mjs, a real Chrome or Edge against the running app) is what finds a page that is wider than the screen. Widgets several slices share (the related-intel graph, the translate button) live in src/shared/ui for the same reason.
- Page copy is English, and that is enforced too (no-nordic-ui-copy): a Russian or Ukrainian system name is data and may appear verbatim in the UI, but a Swedish word in a UI string is a mistake. Foreign words that are genuinely data (the Swedish lexicon, the stopword corpus in shared/lexicons/fillers.ts) live in the lexicon layer, where the rule does not reach.

## Storage and persistence

The store contract, its revision rule, and why a failure must be visible.

- Persistence goes through the async DocumentStore contract (src/shared/contracts/store.ts); repositories are write-through caches that attach a store at startup — so localStorage, PostgreSQL or any DB swap without touching features.
- A document write carries the revision the cache last read (`put(collection, doc, expectedRev)`); a conflict reloads and reapplies the caller's replay function, and a cache that cannot reapply keeps the stored copy rather than the unsaved edit — so two tabs cannot silently replace each other's whole-document writes. The revision lives in the store, never in `updatedAt`; PostgreSQL and browser storage enforce it, while the Lovable Cloud backend reports revision 0 and remains last-write-wins until its managed schema gains a revision column.
- A tab on server storage re-reads the small collections (drones, candidates, procurements, taxonomies and their candidates) when it regains focus or becomes visible, and every two minutes while visible (`use-store-refresh.ts`, wired in `services.tsx`). A repository with a write in flight (`busy`) is skipped and a snapshot read while one was queued is dropped, so a refresh never puts the stored copy over an unsaved edit. Dispatches and sources are not refreshed there: the Sources page reloads them itself. Browser storage has no other writer and is not refreshed. `src/test/store-refresh.test.ts`.
- A write that fails for a reason other than a conflict is retried three times (500 ms, 1.5 s, 4 s: `retryDelaysMs` in `cached-repository.ts`) before it is reported and the cache reloaded, so a dropped connection or a restart no longer costs the edit. A conflict is not retried (it is resolved by reload and replay), a `PermanentStoreError` (the browser's storage is full or blocked) is not retried, and a retry that finds its own write already stored is not an error. `src/test/write-retry.test.ts`.
- The dispatch URL index is built from the cached posts the first time a URL is looked up after `attach()` (`ensureUrlIndex`); before, it held only what the current run had added, so an article stored by an earlier tick was never recognised and a second feed's copy was analysed again. It covers the cached window only. `src/test/dispatch-url-dedupe.test.ts`.
- The dispatch cache is a window, not the table: `load` returns the 3000 newest dispatches (`ORDER` in `postgres-store.server.ts` and `cloud-store.server.ts`) while the table keeps all of them. Anything that must see an older post asks for it by id with `DocumentStore.loadByIds`, through `CachedRepository.hydrate` — `collectSource` preloads the ids a feed re-serves (otherwise an old post looks new, is inserted, and storage rejects it as a conflict), and `claim` hydrates the leased ids (otherwise an old pending post is leased and never analysed). `src/test/dispatch-window.test.ts` holds both cases.
- Storage failures are visible, not silent: a rejected put/remove, a dropped conflict and a failed attach are reported to the shell. The composition root never falls back from server storage to localStorage on its own; an unreachable status call or a partial attach shows the storage error and offers browser storage as an explicit choice, so the analyst never unknowingly edits a second catalog.
- PostgreSQL is selected automatically when the server has DATABASE_URL; schema lives as plain portable SQL in /migrations (also mounted by docker-compose) — keeps the DB vendor-neutral and self-hostable.
- /migrations are applied at server start (plugins/migrate.ts → postgres/migrate.server.ts, recorded in schema_migrations, one transaction, requests wait on it); every file must stay idempotent because adopting an existing database re-runs them all once.
- Server-only DB code lives in *.server.ts files and is dynamically imported inside server-function handlers — keeps the driver out of the browser bundle. A browser-reachable module may not import a *.server module by value (a type-only import is erased at build and stays allowed).
- Shared storage selection happens in store.functions.ts: DATABASE_URL → PostgresStore, else Lovable Cloud → CloudStore (server-only, service role; tables have RLS with no client policies) — browser never talks to the DB directly.

## Ingestion

Two stages, and what is kept out of the drone specs on the way in.

- Ingestion is two-stage: collectors only store raw posts as pending dispatches (no AI); a bounded processor drains the queue and records provenance — keeps scraping fast and AI work resumable. The pipeline itself lives in src/shared/infra/ingest, because the queue, the catalog pages and the server-side collectors all drive it.
- A source's health is read from its history, not only its latest state: every fetch writes a row to `source_fetch_log` (migration 024, shared/infra/sources/fetch-log.server.ts), and `yieldDrift` (entities/source/health.ts) flags a source that keeps failing or that returns nothing where it used to yield — the second is a broken parser, which the failure streak never sees. A fetch is retried once on what a second try can fix (timeout, network error, 429, 5xx), never on another 4xx. The log is bookkeeping inside the existing sync, best effort, and never changes the sync's result.
- A source the health check turned off is probed once a week (`probeDue`, `runSourceProbes`; `SOURCE_PROBE`) and re-enabled when the probe returns posts, with a ledger event, so a site that was down for a month does not stay dead until someone notices. Only a system disable is probed: the health check is the only writer of `disabledReason`, `reenable()` clears it, and an analyst's toggle never sets it — an analyst's "off" is a decision automation does not overturn. Eight failed probes leave the source for a person.
- Financial/deal spec keys (contract_value, *_funding, total_cost…) are split out of extractions at the pipeline boundary (entities/procurement/routing.ts) into the procurements collection; only unit_cost stays a drone spec — keeps deal figures out of consensus.
- Activity figures (launched, intercepted, delivered, produced, kills, ordered — "launched more than 2,800 in August") are not properties of a system: `mergeSpecs` splits them out at every ingest path into `Drone.activity` (entities/drone/activity.ts), each with its quantity, bound, counted unit and period, and the catalogue repair moves ones stored as specs. Consensus never reads activity; it is a series, shown in the dossier's Activity panel. An attribute that only mentions an event (launch weight, production timeline) stays a spec.

## Heuristics, rules and evaluation

How the deterministic engine learns without being able to hurt itself.

- Language vocabulary (money, units, cues) lives in per-language lexicons in src/shared/lexicons, shared by heuristic extractors and normalization; heuristics are split into names, facts orchestrator and per-class/fact-family extractors that read only lexicons — adding a language, term or system class never touches unrelated code.
- Heuristic evaluation (src/shared/infra/evaluation) is read-only: it only calls heuristic.extract and reads candidates; agreements export to src/test/fixtures/eval-corpus.json, which eval-corpus.test.ts replays — so heuristic changes can't silently regress real reports.
- Dynamic heuristic rules live in dynamic_rules (migration 010) and reach the engine only as an immutable RuleSnapshot (src/shared/contracts/rules.ts); the server registry (shared/infra/heuristics/rule-registry.server.ts) refreshes it by version with a TTL and never throws — so extract() stays synchronous/pure and ingestion survives DB outages.
- A dynamic rule becomes active only through the in-process sandbox (src/shared/infra/evaluation/sandbox.ts, read-only): zero fixture regressions, no F1 drop, a measurable gain — and activation re-runs it against the rules active at that moment (shared/infra/evaluation/rule-sandbox.server.ts). The DSL carries literal terms only, never regex — so generated rules cannot backtrack or reach outside the words they name.
- After an AI pass, each stored spec records the AI's verdict on the heuristic's observation in `provenance` (both/heuristic/ai; entities/drone/extraction-gates.ts), and evaluation scores AI-dropped claims as rejected — so the heuristic is never measured against its own ingest-time output while the stored union still never drops a deterministic fact.
- Generated rules go sandbox → shadow → active; auto-promotion (shared/infra/evaluation/autonomy.ts) needs 48 h shadow on unseen reports, zero conflicts, ≥95 % shadow precision and ≥95 % trust from ≥20 analyst decisions in the category, max 2/day, and a nightly circuit breaker compares all-active vs active-minus-last-24h on the same sample — so autonomy is earned per category and rolled back on harm, never on data drift. `RULES_AUTOPROMOTE=off` disables it.
- A quarantine is not the end of a rule or of its claims. The posts behind the claims a quarantined rule shaped are re-analysed without it (shared/infra/evaluation/rule-sandbox-replay.server.ts, `RULE_REPLAY`), found through claim lineage, because removing a rule alone leaves what it filed in the catalogue. And a generated rule the circuit breaker quarantined returns to shadow once after seven days (rule-sandbox-probation.server.ts, `RULE_PROBATION`), where the unchanged promotion policy decides again — so a breaker tripped by one bad night does not need a person to undo it. Aliases and stopwords never return unattended (identity is the high-risk tier), an analyst's quarantine is never undone, and a second quarantine is final. Both write a decision event to the ledger.

## The catalogue model

Typed relations, families, origin, observations and names: identity is the high-risk tier, so most of it is proposed and never applied.

- Relations between entries are typed and directed (`Drone.relations`, `SystemRelationClaim`; entities/drone/system-hierarchy.ts): `variant_of`, `derived_from`, `subsystem_of`, `effector_for`, `carried_by`, stored once on the entry that depends on the other, and `counterpart_to`, stored once for both. The other end reads them through the inverse (`has_variant`, `parent_of`, …), which is never stored. `systemClass` says what an entry is; a `family` (Geran, Shahed) is an umbrella its variants point at. system-hierarchy.ts is the one reader - the dossier, the counterparts page, catalogue cards, the related-intel graph and the briefing digest all go through `resolveRelations` - and it reads the legacy `variantOfId`/`variantIds`/`counterpartIds` with them until the repair has copied those over; catalogue operations (`linkSystems`, `unlinkSystems`, `reviewRelation`, merge, remove) write both and unlink both sides, so a legacy link left behind cannot be revived. Inherited specs exist only in a comparison view (`compileEffectiveSpecs`), never in an entry's own specs or in consensus.
- Family clean-up is proposed, never applied (`familyProposals`, entities/drone/family-audit.ts; the Families page): an entry two or more others are numbered after is a family, a numbered entry not linked to it is its variant, an alias that is another entry's name or a designation on a family is misfiled, and an entry sharing most of a family's names is a merge. Each proposal is an existing catalogue operation the analyst runs; a turned-down one is recorded (a rejected relation, `distinctFrom`, a reviewed alias) and not proposed again. Identity is the high-risk tier: nothing here runs unattended. The catalogue repair copies legacy links into typed relations (`legacyRelationsToMigrate`), once each, never a second family.
- A system's origin is a decision, not a first impression (`originClaims`, `originReview`; entities/drone/origin-audit.ts): every promote and merge records the country the report gave for that system - its own per-system extraction, never a digest's top-level origin - and the catalogue repair backfills them from stored candidates. An unknown origin two reports agree on with none disagreeing is filled by the repair; a stored origin most reports contradict is only proposed on the dossier, because a majority of model readings is not proof (Geran-2 is an Iranian design built in Russia). The analyst's `setOrigin` outranks every report, and the countries it turns down are never proposed again.
- A variant an entry has been carrying (PAC-3 answering to "PAC-3 MSE" and holding its figures) is split out by the analyst only (`splitVariant`; entities/drone/variant-split.ts, shared/infra/catalog/split.ts). The new entry is named by one alias; the other aliases and the claims whose quote uses the variant's distinguishing words are preselected for the analyst to edit, never moved unattended. Each move is the ordinary cross-system move, so it stays on the parent as moved evidence and is returned one by one, and the new entry is linked `variant_of` the parent.
- A payload or a sensor reaches the catalogue twice: as an observation (what a report said the system carries) and as a spec (the figure — payload capacity, warhead mass, camera count). The panels read both (entities/drone/observations.ts), because the observation lists are thinly filled and the specs are where most of that knowledge is; the prompt says which is which (shared/contracts/extraction-prompt.json), so a list of what the system carries never becomes a spec and a figure never becomes a list.
- Names match after a system's name only through real Russian/Ukrainian case endings, the bare stem and the English plural (`CASE_ENDINGS`, entities/drone/name-key.ts), never "any few letters": that read "контракт" (contract) and "contrast" as Contra and "лютого" (February) as Lyutyi. A change to name matching is an identity change: measure it over the archive before it ships.

## Claims, review and verification

Who outranks whom: the analyst's verdict, then the deterministic verdict, then the second reader. See also the `autonomy-change` skill.

- An analyst's verdict on a spec claim lives on the claim (`SpecClaim.review`, entities/drone/claim-review.ts), never in a separate table, and outranks every automated verdict; it is the ground truth the automation is scored on: the evaluation reference (`verifiedReference` applies it over the verifier's verdict in both directions), live regression fixtures (`verifiedFixtures`, with `analystFixtures` kept for analyst-only call sites) and the trust of the contradiction check — so one person's correction reaches every loop, works in every store and survives re-analysis.
- A claim the analyst says belongs to another attribute is moved, not just ruled out (`moveClaim`, entities/drone/claim-review.ts): it keeps its place in the report, stops counting on the attribute it was misfiled under, and is filed under the attribute the analyst names, with the reading the analyst gives — because a speed read as a height is not a wrong figure, and ruling it out alone would throw the figure away. Undoing the verdict undoes the move with it, and the filed copy is the analyst's own claim, so a re-read of the post leaves it alone. A unit fix never counts as agreement with such a verdict: it would have applied a value to a figure that does not belong there.
- Unit slips and impossible figures are found deterministically (entities/drone/auto-correction.ts) and recorded as `SpecClaim.autoCorrection`; the sync job (shared/infra/ingest/auto-correct.ts) applies a kind of correction only while analysts' answers on it meet the earned-trust bar (shared/infra/ingest/earned-trust.ts), recomputed every run — so a correction is a proposal until earned, rolled back when agreement falls, and `AUTOCORRECT=off` keeps every one a proposal (every loop switch is defined once in shared/infra/autonomy/switches.server.ts).
- Every machine claim carries a deterministic verdict (`SpecClaim.verification`, entities/drone/verification.ts, a barrel over the verification-*.ts modules: check factory and `VERIFIER_VERSION`, evidence, unit/bounds, identity, wording, sources, claim, drone, coverage): quote in the post, unit, bounds, target (a figure whose clause names another target than its attribute - "vehicles at 12 km" filed as micro-drone range - fails; entities/drone/target-check.ts, silent when no target is named), value (the quote states the claim's figure or most of its words - a true sentence about something else, quoted as the evidence, leaves the claim `uncertain`, never `rejected`, because a declined number word or a translated quote cannot be matched deterministically; entities/drone/value-in-quote.ts), attribute words (the words beside the figure fit its attribute: a height whose words make it a distance - "hit targets up to 2,000 km away" - fails, entities/drone/altitude-check.ts; a cruise speed "up to"/"розігнати до" is a top speed and fails, and the reverse, entities/drone/speed-check.ts; silent when the words name neither), and identity — anchored to the sentence carrying the quote, matched with the extractor's own `mentionsName` (entities/drone/name-key.ts) over the same `catalogNames` (entities/drone/catalog-names.ts), and `uncertain`, never `pass`, when that sentence names no system, with one exception: a sentence that opens with a continuation word ("It …", "Він …", "Он …") passes at lower confidence when the sentence before it names this system and no other. It shows the extractor read the post correctly, not that the post is right, and it is measured only: `claimCounts` does not read it, so an uncertain or rejected claim still counts in consensus until a later phase of get_human_out_of_the_loop_plan.md says otherwise. Bumping `VERIFIER_VERSION` re-verifies the catalogue. With PostgreSQL that run is on the server (`verification:run`, hourly; shared/infra/verification/verify.server.ts), reading post text straight from the archive, because the store caps the dispatches it loads and a run over the browser's window judged older claims "not in the archive"; in browser storage the backfill runs in the browser in yielding chunks; against a last-write-wins store it runs only when asked. Either way it and never re-judges without its post a claim that was checked against one (a pruned post, an unarchived paste). Claims carry the archived post they came from (`sourceId`, stamped through the intake queue by `Candidate.dispatchId`); older claims written without it are linked back by their unique `outlet · URL` source before they are verified.
- A claim records what produced it (`SpecClaim.lineage`, entities/drone/claim-lineage.ts): prompt version and hash, pipeline version, rule-set version, the generated rules that shaped its spec, the name or alias that resolved the post to the system, and the post's content hash. It exists so a reversal is a query instead of a search: which claims a rule shaped, which arrived through a rule alias, which prompt version yields claims that verify. A claim without lineage means unknown, never none, and only the content hash is backfilled. The extraction prompt carries a hash that a test pins with its version (src/test/prompt-guard.test.ts), so a prompt edit cannot go unversioned.
- Independent sources are counted by text as well as by outlet (entities/drone/verification-sources.ts): two outlets whose posts have near-identical content hashes are one source, because a repost is not a second witness. A claim without a hash is grouped by outlet only.
- The evidence brake and the verifier fold text the same way (shared/infra/ingest/evidence-brake.ts uses the verifier's `fold`), so a quote cannot pass one and fail the other on Unicode forms alone. An AI-made quote that fails gets one repair call, accepted only when the returned passage is in the post and carries the figure's digits; what is dropped is counted on the dispatch, because a silent drop cannot be measured.
- The second reader is also measured without a person (shared/infra/verification/controls.server.ts, `verification:controls` hourly, migration 025): it is shown verified claims whose figure was changed to one the post does not contain, through the same question builder as a real claim (`entailmentQuestion`), and a "supported" is a false support. The rate is reported overall and per attribute family and language against the low-risk budget. It complements the audit and does not replace it: the controls test whether the reader notices a wrong figure, not whether it files a figure under the right system. It never reads `verification_audit` and writes nothing to the catalogue.
- Scores are measured against the verified reference (`verifiedReference`, shared/infra/evaluation/reference.ts; evaluation.ts is a barrel over reference, reference-fixtures, compare, coverage, posts, sampling, evaluate and fixture-check): a verified claim counts as an expected positive even when the AI dropped it, a rejected one as an expected negative, and an uncertain one is excluded from every score — never a miss, never a false positive; a claim nobody has judged falls back to the stored extraction, so an unverified catalogue behaves as before. `ReferenceCoverage` (overall and per key) is reported beside every score — evaluation report, Evaluation page, sandbox verdict, shadow line — because a 95 % F1 on 5 % verified coverage is not evidence. Fixtures come from `verifiedFixtures` (verified → expect, rejected → forbid, uncertain → neither); mining, shadow scoring and adjudication use the same reference, and nothing that learns reads the audit seed set.
- Autonomous decisions are written to `autonomy_events` (migration 018, shared/infra/autonomy/ledger.server.ts) with actor, target, before/after and a `reversed_by` link; decision events are kept forever and only the kinds in `HEARTBEAT_EVENT_KINDS` are pruned. An event kind is added to `AUTONOMY_EVENT_KINDS` in the same change as the code that writes it.
- How often `verified` is right is measured by a person, never assumed (`/audit`; entities/drone/audit.ts, shared/infra/verification/audit.server.ts, migration 019): the system draws verified claims at random with a recorded seed, the person answers one question per claim, hidden controls catch inattention - a verified claim shown with a figure the post does not contain, wrong by construction, and a "yes" on one voids the ~25 answers around it, not the batch (the first sessions' controls rested on the identity check and may be disputed by the owner; migration 021), and the gate is one analysis over a frozen probability sample (the formal evaluation: 200 verified claims drawn in proportion to three language strata - English, Cyrillic, other - entities/drone/audit-design.ts; migration 026). The bound is exact for that design, taken over every way the wrong claims could be spread across strata (entities/drone/audit-statistics.ts), with no approximation; when it cannot be computed within its limit the result is `incomplete`, never a pass. A claim a person answered "cannot tell" counts as an error in the bound that decides, the best case is shown beside it, and a claim shown again after a failed control voided its answer is the same sample unit (`audit_sample_units`), counted once. The earlier 100/150/200 looks at the non-probability draws remain as information (`interim`) and never decide. The person's answer is the reference: the gate measures agreement with that first answer, and the owner's later `second_look` is a note beside it, not a replacement; an answer that is changed afterwards is logged, append-only, and migration 027 keeps a presentation tied to the sample unit of its own batch and claim, so a retry can only repeat the unit it follows. An audit answer measures the verifier and never becomes `SpecClaim.review`, and the frozen seed set lives only in `verification_audit` — every learning loop reads the analyst's review, and nothing that learns may read the seed set.
- A second reader checks what the deterministic checks leave uncertain (`SpecClaim.entailment`; entities/drone/entailment.ts, shared/infra/verification/entailment.server.ts, `verification:ai` hourly): a model that extracted none of the post's claims, shown the post and the bare claims but never the extractor's quote, answering with a passage that must be in the post or the answer is `uncertain`. Its verdict has four states - supported, contradicted, not_found, uncertain; a stored legacy "unsupported" is kept as written and never re-read as either of the two it was split into (entities/drone/entailment-verdict.ts). A reading carries the fingerprint of the claim it was given on and the hash of the exact input, so a claim changed under an unchanged post is read again. The audit freezes the reader's state when a claim is drawn (`verification_audit_reader`, append-only, migration 026): the reading at draw is kept apart from later ones, and a reading that cannot be shown to describe the claim as drawn is kept as legacy history, never counted as the one at draw. Its spend is counted per day in `ai_token_usage` (migration 020) and stops at the ceiling (`VERIFIER_DAILY_INPUT_TOKENS`/`_OUTPUT_TOKENS`). It is measured, not acted on: no claim's state and no consensus reads it until its agreement with the person's audit answers (the Audit page) says its "supported" can be trusted; `AI_VERIFIER=off` stops it.
- A claim's source unit is only a unit that is evidenced for that claim (entities/normalization/claim-source-unit.ts): in the stated value or beside the figure in the quote. `SpecAttribute.unit` is often the attribute's canonical unit and is never read as one claim's source unit; an extractor unit the text contradicts is a `conflict` and fails the unit check, one nothing confirms is shown as unverified. A figure whose unit is not evidenced (`unknown`, or only the extractor's, `unverified`) is held back from numeric consensus and its unit check is `uncertain`; a conflict fails it (entities/drone/unit-policy.ts). The claim and its text are kept, and consensus shows "unit unknown" and counts what it held back (`heldBack`). A figure a person or the curated catalogue gave with its unit (an analyst's entry, a seed claim, a structured reference import) counts as declared. `normalized.raw` is never taken for the source's words. A load factor is its own dimension (`g_load`, shown as "g"), parsed only where the attribute says so, and never converts to mass or acceleration.
- Consensus compares claims as intervals on the attribute's canonical unit (entities/drone/consensus.ts): points and range midpoints give the median, one-sided bounds are compared but never feed it, and sources are clusters of one outlet or near-identical text, so a repost with another figure is still one observation. Whether two figures disagree is the registry's tolerance for the attribute (entities/normalization/core-registry.ts). A range a source stated is kept with its claim and source (`explicitRanges`); the spread between point sources (`observedSpread`) is never shown as a source range.
- A sentence can assert several things about different parties; `AssertionFrame` (entities/drone/assertion-frame.ts) separates who acts from who owns a figure, and its validator (entities/drone/assertion-validation.ts) is checked against frozen fixtures. There is no producer in the ingest flow yet: the checks run on fixtures only, and a check is written to `autonomy_events` as `assertion_frame_check`, one event per post, not pruned.

## Module structure, switches and proposals

The conventions that keep the next change small.

- Big modules are split into concern files behind a barrel that keeps the old import path (`ingest/auto-ingest.ts`, `evaluation/evaluation.ts`, `infra/catalog-operations.ts` over `infra/catalog/*`, `entities/drone/verification.ts`, `infra/storage/local-repository.ts` over `storage/local/*`, `evaluation/rule-sandbox.server.ts` and `evaluation.server.ts` over their `*-<part>.server.ts` files): a new concern gets a file, and importers outside the area never change. A barrel only re-exports; logic lives in the part files. Formatting helpers two slices need (`pct`, `pctPrecise`) live in shared/ui/format.ts, not in a slice.
- Every on/off switch of an autonomous loop (`RULES_AUTOPROMOTE`, `AUTOCORRECT`, `AI_VERIFIER`, `RULE_PROBATION`, `RULE_REPLAY`, `SOURCE_PROBE`) is defined once in shared/infra/autonomy/switches.server.ts and read with `autonomySwitchEnabled` (unset or empty keeps the default, on; "off" in any case turns it off); a job in SCHEDULED_TASKS names its switch in `switch`, and a test checks the name exists. A job names one switch only, so `RULE_REPLAY` and `SOURCE_PROBE`, which gate a step inside a job or action that already names another, are read at the step and do not appear in the job table. A new loop gets its switch there, not a raw `process.env` read.
- What a learner may ask to change is a `Proposal` (shared/contracts/proposals.ts; plan §5.2): data, admitted by `admitProposal` (shared/infra/proposals/admit.ts) only if its kind has a registered applier, and with its risk tier assigned by that applier from the kind and payload, never taken from the proposer — so an AI cannot call its own change low-risk or smuggle behaviour through a payload.
